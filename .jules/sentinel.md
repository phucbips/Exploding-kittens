## 2025-02-18 - Firebase Race Condition in Room Management
**Vulnerability:** The application used a "Read-Then-Write" pattern (get + set) to join game rooms and create new rooms. In a concurrent environment, two users joining at the same time could read the same state, add themselves, and overwrite each other's changes, leading to data loss and corrupted game state. Similarly, room creation could overwrite an existing room if a random ID collision occurred.
**Learning:** Firebase Realtime Database does not support atomic operations via `get` and `set`. Concurrency must be handled explicitly using `runTransaction`. Also, `runTransaction` runs optimistically with local cache. If data is not cached (e.g., first join), `currentData` is null, which can cause logic to abort prematurely. Using `{ applyLocally: false }` or ensuring data is loaded (via `get`) before transacting is critical for "Join" operations on new data.
**Prevention:** Always use `runTransaction` when modifying data based on its current value (e.g., appending to a list, incrementing a counter). For critical operations like room creation, ensure uniqueness checks are atomic or use transactions to safely abort if data exists. For joining, verify existence and load data first or use server-only transactions.
